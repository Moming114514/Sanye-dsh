# 三叶项目 · 现状与规划（给 AI 评审用）

> 目标读者：另一个 AI 或工程师。请先读 §0 约束，再给建议。
> 本文只写事实与取舍，不写宣传。所有数字来自线上实测。

---

## 0. 硬约束（决定一切）

| 项 | 值 | 含义 |
|---|---|---|
| 服务器 | 2 vCPU / 4 GB（可用 3.6 GB）/ 40 GB / 无 GPU | 不能跑本地模型、不能加常驻服务 |
| 内存 | 曾 OOM 一次（已加 zram 1G + swap 2G + swappiness 60） | 任何"多进程常驻"方案基本否决 |
| 预算 | 每天 ≤ ¥8（实测 ¥2~4） | 每多一次模型调用都要算账 |
| 人力 | 1 人（学生），每天 20~30 分钟 | 方案必须自愈、可观测、少运维 |
| 形态 | 单角色个人使用，非平台、非多租户 | 不要 K8s / 多实例 / 分布式 |
| 模型 | DeepSeek（API），无自建推理 | 不能用需要本地权重的方案 |

**不需要的建议**：本地大模型、GPU、向量数据库、K8s、多容器编排、前端框架迁移、全量重写。
**欢迎的建议**：在不加内存、不加每轮调用的前提下，降低"判停错误率"与"人味不足"。

## 1. 架构（当前）

```
QQ 客户端 ←→ NapCat（OneBot v11，docker，~250MB）
                ↕ WebSocket
           bridge（Node，systemd，~160MB）
             ├─ 7 个扩展钩子（ext/*.js，32 个模块）
             ├─ 30 个 MCP 工具（core-min 档，schema ~20K 字符）
             ├─ 状态文件（人格/记忆/规则，全在磁盘）
             └─ HTTP :3100（给面板/调试）
                ↕
           DSH（agent 运行时，Node，~600MB）→ DeepSeek API
           ASR：sherpa-onnx（systemd socket 激活，空闲 300s 退出）
面板 her-console（:7800，只读状态 + 改配置）
```

关键性质：**"她"= 磁盘上的文件**（人格 4 层 + 记忆 + 状态），进程只是壳。换运行时只需重写 7 个钩子（见 `docs/DECOUPLE.md`）。

## 2. 实测数字

| 指标 | 值 |
|---|---|
| 入口量（最热闹的群） | 100 条消息 / 16 分钟 ≈ **373 条/小时** |
| 其他群 | 57 / 7 / 3 条/小时 |
| 每天唤醒轮次 | ~100 |
| 每轮平均成本 | **¥0.022**（¥2.2/天） |
| 成本构成 | 缓存未命中输入 ~50%、命中 ~24%、输出 ~5%、峰时加成 ~13% |
| 缓存命中率 | 96~97% |
| 人格注入 | 私聊 ~9K 字符 / 群 ~9K 字符（4 层，群只装语气+场景） |
| 记忆卡注入 | 24 条 / ~2600 字（全量 600 条） |
| 工具 schema | 30 个 / ~20K 字符（balanced 是 50 个 / 29.7K） |
| 媒体（图/表情） | 每天 ~30 条，自动附图后"看到"率 0 → 100% |

## 3. 关键设计决策（含理由）

| ID | 决策 | 理由 | 复查条件 |
|---|---|---|---|
| D-001 | 人格分 4 层（核心/语气/日常/场景），群只装语气+场景 | 群聊不需要"我是谁"的长篇，省 token | 群里显得没底气时改全量 |
| D-002 | 内联补丁 → 7 个扩展钩子 + manifest 清单 | 补丁曾达 126 处，改一处崩三处 | 再出现 3 处以上硬编码就继续迁 |
| D-003 | 判断用**本地规则打分**（0 成本），只在边界分考虑小模型 | 每条消息都调模型 = 每天 ¥0.5+ | 判停准确率 <80% 时再加一层 |
| D-004 | 学说法只学 1 个来源（群里某机器人），只学"框架"不学口头禅 | 多源会串味 | 样本 >10 条后评估 |
| D-005 | 看图不靠模型自觉，由 bridge 自动附图 | 实测模型 0% 主动调工具 | 模型换代后重测 |
| D-006 | 工具裁剪到 30 个（core-min） | schema −32% | 有功能调不到时逐个补 |
| D-007 | 免费额度（第三方）只用于可丢弃的支线 | 条款/封号/数据外流风险 | 官方涨价时再评估 |
| D-008 | 不换 NapCat（注入式，功能全），换壳只做文档 | 迁移成本 > 收益 | QQ 更新导致彻底不可用时强制换 |

## 4. 最近两周做了什么（按层）

- **感知**：看图链路三断点全部修复（媒体判空 / 下载顺序 / 描述注入），改为 bridge 自动附图（8MB 降采样）；媒体统计可观测。
- **判断**：7 个闸门收进 `speak-policy.js` 适配层（预测/实际对照日志）；抽样放行不再降级为"只回一句"；新增"活跃期"（主人叫醒后 10 分钟正常对话，说"回去"退出）；静音对"主人直呼"放行。
- **表达**：8 条铁律、禁 3 种句式、13 个套话词；学说法样本带"短句 + 框架"。
- **记忆**：倒排索引召回（0.34ms/600 条）、按会话隔离、每月归档。
- **成本**：人格精简（1.36 万 → 0.9 万字符）、工具 50 → 30、ASR 按需、zram。
- **运维**：systemd + watchdog + 自检（30 分钟）+ 面板一屏总览 + 每日 18:00 异常提醒。

## 7. 想请评审回答的问题

1. **判停**：373 条/小时的群里，除了"本地打分 + 边界抽样"，有没有**零/低成本**的方法判断"哪几条值得回"？（我们现在只有：叫名字、问句、求助词、@别人、长度、重复）
2. **多话题**：三个人同时说话时，怎么低成本挑"最值得接的那条"？用一次小模型做 1/2/3 选择值不值？
3. **人味**：有没有可操作的规则（不是"要自然"），能直接写进提示词、并且**不增加每轮 token**？
4. **记忆**：600 条记忆每轮挑 3~5 条，除了关键词倒排，有没有**零内存成本**的更好办法？
5. **可观测**：如何用**最小改动**定位"这次判错是哪一层导致的"？（现在有 7 层闸门日志，但人肉看很累）
6. **稳定性**：2C4G + systemd + watchdog + 自检，够不够？有没有"不加重"的兜底手段？

## 8. 已明确不做

- 多角色 / 多租户 / 对外服务化
