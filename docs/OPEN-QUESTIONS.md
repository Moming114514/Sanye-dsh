# 待外部咨询的问题（2026-11-06）

> 用法：每条都是「我们的做法 → 卡点 → 想问什么」，可整段截图。
> 背景：单台 2C4G 阿里云，Node 单进程（bridge 1.6 万行）+ NapCat + DeepSeek API，QQ 机器人，日预算 ¥8。

## Q1 记忆检索：600 条规模，倒排 + 别名够不够
- **做法**：JSON 记忆卡（约 600 条），倒排索引按 CJK 二元组建 posting，查询时 `Σlog(1+N/df)` 打分；今天加了 15 组同义词别名（米饭↔大白饭）。
- **卡点**：换个说法仍会漏（"那天"、"上次那个"这种指代完全查不到）。实词重合度只有 0.08。
- **想问**：600 条这个量级，值不值得上 embedding（bge-small 量化 ≈30MB，但 2C4G 只剩 1.7G）？还是先把"指代消解 + 会话窗口"做扎实更划算？

## Q2 人格卡长度与"像人"的关系
- **做法**：人格分四层（核心 1 千字 / 语气 1.5 千字 / 场景 / 日常），群聊只装语气+场景。
- **卡点**：从 2.3 千字砍到 1.5 千字后，不确定是"更聚焦"还是"丢了场合感"。
- **想问**：有没有可信的做法判断"删哪一段会伤到人味"？30 条金标 + rubric 判官够不够？

## Q3 群聊多话题选址
- **做法**：多人同时说话时，目前只回"最新一条"或"@ 我的那条"。
- **卡点**：群里三条线在聊，她经常接错线（接了个已经不聊的话题）。
- **想问**：有没有比"@ > 叫名字 > 引用 > 问句 > 抽样"更好的选择策略？用小模型做一次选择题（1/2/3）值不值？

## Q4 工具调用可靠性
- **做法**：53 个 MCP 工具，靠提示词要求"先看图再开口"，模型经常不调。
- **卡点**：后来改成"bridge 直接把图附进 prompt"绕过，但通用场景（查记忆、发空间）仍靠模型自觉。
- **想问**：除了"把工具结果预取进上下文"，有没有更稳的模式（比如强制 function-call 前缀、或两段式：先判意图再调工具）？

## Q5 上下文压缩
- **做法**：无压缩，只按段截断。
- **卡点**：长对话后 prompt 里旧消息占大头，且"易变段放末尾保缓存"已有约束。
- **想问**：滚动摘要（每 N 轮压一次）vs 分段 token 预算，哪个在低预算 + 强缓存依赖的场景下更划算？

## Q6 记忆写入策略
- **做法**：每条消息过规则，命中关键词/情绪/约定才记，带 importance 与衰减。
- **卡点**：记了不少琐碎句（"我在改"），也漏掉关键约定。
- **想问**：有没有更靠谱的"该记/不该记"启发式？是否需要写入时做一次事实抽取（谁对谁做了什么）？

## Q7 人格"养成"
- **做法**：核心卡手工维护；每周从纠正里归纳"学到的规则"写进独立层（未实现）。
- **卡点**：担心越养越漂移（规则互相打架）。
- **想问**：learned 层的容量、审核节奏、防漂移机制，有没有成熟做法？

## Q8 双实例/单实例
- **做法**：systemd 管 bridge，但 DSH 插件也会自己 spawn，导致锁冲突。
- **卡点**：插件自启时会抢锁，systemd 每 5 秒重启一次。
- **想问**：这种"宿主也管、systemd 也管"的场景，标准做法是什么（drop-in 禁用 + 只留 systemd？还是反过来）？

## Q9 QQ 侧媒体读取
- **做法**：NapCat 的 `get_image` 拿新地址，超 8MB 用 ffmpeg 降采样，动图抽 3 帧。
- **卡点**：偶发 400（地址过期）、部分表情 CDN 已失效。
- **想问**：有没有更稳的媒体缓存方案（本地缓存 + 内容哈希）？

## Q10 评测
- **做法**：面板人味指标（句长、实词重合度、问号占比、总结句比例），靠人工打标。
- **卡点**：打标 10 条才发现样本太少；且没有"回归测试"。
- **想问**：小团队（1 人 + AI）做 LLM 应用，最低成本的评测流程该怎么搭？
