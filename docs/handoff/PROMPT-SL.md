# 提问：把 QQ 通道从 NapCat 换成 SnowLuma（或同类注入方案）

> 复制给另一个会话。它需要先读 HANDOFF.md，再回答。

## 背景

现在跑的是：Ubuntu 云服务器 + Docker 里的 **NapCat**（协议端，无头），通过 **OneBot v11** 和我们的桥接通信。
桥接本身是「SnowLuma SDK + OneBot 双兼容」的（`config.json` 有 `channel` 段，旧段优先）。

用户听说有人用 **SnowLuma** 成功了，怀疑我们当初失败只是因为「二维码有延迟、扫不上」，想再试一次，并且**不想长期维护两套兼容**。

## 要回答的问题

1. **技术上能不能在 Linux 服务器上跑 SnowLuma？**
   - 它需要什么前置（QQNT 客户端？Linux 版 QQ？图形环境？）；
   - 无头服务器上登录（扫码/密码/设备锁）怎么解决，二维码延迟是不是真问题；
   - 如果 SnowLuma 不行，**同类注入方案**（如 LLOneBot + LiteLoaderQQNT）在 Linux 上是否可行，二者差别是什么。

2. **换过去对我们现有系统的影响面**：
   - 事件/消息格式差异（OneBot v11 字段：`post_type`、`message_type`、`sender`、`message` 段类型、`reply`、`at`、`mface`、合并转发）；
   - 我们的 `src/ext/*` 里有 31 个模块依赖这些字段，哪些会坏；
   - 图片/表情/动图链路（NAPcat 的 `get_image`、媒体 URL 过期）换了之后是变好还是变坏；
   - `bot.getGroupInfo` / `get_stranger_info` / `get_cookies` / `get_group_msg_history` 这些能力是否都还在。

3. **迁移与回滚方案**：
   - 能不能**并行跑**（两个通道同时在线，用白名单切换）而不是一次性替换；
   - 回滚到 NapCat 需要多久；
   - 需要改哪些文件（尽量只改配置，不改代码）。

4. **给一个结论**：值得换 / 不值得换 / 有条件（什么条件）。

## 约束

- 不要动线上（只允许只读检查与查资料）；
- 回答前先确认哪些是**你实际验证过的**、哪些是**看文档/推测的**，分开写；
- 如果结论是「换」，给出分阶段步骤，每步带验收与回滚；
- 如果结论是「不换」，说明现在 NapCat 的哪个具体短板才真的需要解决（例如媒体过期、群历史窗口），以及能否在 NapCat 上解决。
